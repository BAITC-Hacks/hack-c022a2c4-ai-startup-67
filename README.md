# HackAlem — Money Graph

Объяснимые признаки наблюдаемой сети денежных переводов — направленного графа.
Pipeline проверяет входные parquet-файлы и формирует одну строку на клиента,
сохраняя в том числе изолированные узлы.

Основной язык README — русский. Английские термины при необходимости приводятся
рядом с объяснениями; имена файлов, признаков и команды сохраняются как в коде.

## Запуск

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python pipeline.py --data /path/to/data --out out
```

Замените `/path/to/data` на путь к папке с `nodes.parquet`, `edges.parquet` и
`transactions.parquet`. Результаты: `out/node_features.csv` и
`out/diagnostics.json`, а также `out/nodes_roles.csv` с ролями. Данные и выходные файлы исключены из Git через `.gitignore`.
Обязательные схемы и строгая сверка сумм и количества транзакций с рёбрами
описаны в `utils/validation.py`. В тестах и документации нет реальных
идентификаторов клиентов.

## Структурные признаки (graph features)

Все базовые столбцы сохранены: `gid`, `depth`, `is_seed`, `in_deg`, `out_deg`,
`in_kzt`, `out_kzt`, `in_tx`, `out_tx`, `pagerank`, `pass_through`,
`truncated_by_depth`, `total_kzt`, `total_tx`. Существующий PageRank взвешен
по `sum_kzt`, использует alpha 0,85 и рассчитывается только один раз.

Модуль `analytics/graph_features.py` добавляет:

- `betweenness`: точную центральность посредничества на **направленном невзвешенном**
  графе со стандартной нормировкой NetworkX. Денежные суммы не используются
  как расстояния при поиске кратчайших путей.
- `hub_score`, `authority_score`: HITS из NetworkX на невзвешенной структуре графа
  с фиксированным начальным вектором из единиц. Если оценки определены, они
  неотрицательны и сумма каждого вида оценок равна единице. Высокая hub-оценка
  характеризует отправителей в сторону важных получателей, authority-оценка —
  получателей от важных отправителей. Это описание структуры, а не назначение ролей.
  Для изолятов и графов без рёбер оценки равны нулю. При сбое алгоритма или
  некорректных оценках узлы с рёбрами получают NaN, причина записывается в
  диагностику, pipeline продолжает работу. При кратном максимальном сингулярном
  значении решение HITS может быть неединственным, поэтому его следует
  интерпретировать осторожно.
- `weak_component_id`, `weak_component_size`: номер и размер компоненты слабой
  связности. Компоненты упорядочены по минимальному gid. Номера воспроизводимы
  для одного и того же графа, но не являются постоянными метками клиентов.
- `direct_seed_in`, `direct_seed_out`: количество уникальных seed-клиентов,
  непосредственно отправляющих деньги узлу или получающих деньги от него.
  Seed-клиенты — исходные клиенты, от которых собирали граф.
- `reachable_seed_count`: количество seed-клиентов, от которых узел достижим
  по направленным путям. **Seed считается достижимым от самого себя по пути
  длины ноль.** Каждый seed учитывается для узла не более одного раза.
- `min_seed_distance`: минимальное число направленных переходов от любого seed;
  для seed равно нулю, для недостижимых узлов — NaN. Исходный `depth` сохраняется.
  Диагностика отдельно считает расхождения глубины для достижимых узлов
  и количество недостижимых узлов.
- `largest_in_sender_share`, `largest_out_receiver_share`: максимальная сумма
  по одному контрагенту, делённая на соответствующую наблюдаемую сумму потока.
- `incoming_amount_hhi`, `outgoing_amount_hhi`: сумма квадратов долей контрагентов
  (индекс концентрации HHI). Чем ближе к единице, тем сильнее концентрация.
  Если на соответствующей стороне нет положительного денежного потока,
  и максимальная доля, и HHI равны нулю.
- `in_avg_tx_kzt`, `out_avg_tx_kzt`: наблюдаемая сумма, делённая на количество
  транзакций; при нулевом количестве — NaN. `counterparty_balance` равен
  `out_deg - in_deg`, а `degree_ratio` — `out_deg / in_deg`; при нулевом
  знаменателе отношение равно NaN.
- `is_in_short_cycle`: точный признак участия в направленном цикле длиной
  не более шести рёбер, включая петли. Для каждого узла ограниченный поиск
  в ширину (BFS) по обратному графу находит узлы, из которых можно вернуться
  за пять переходов, после чего проверяются исходящие соседи. Сложность
  в худшем случае — O(V(V+E)), дополнительная память поиска — O(V).
  Полный перебор и подсчёт циклов не выполняются.

## Дневная активность и повторные связи (temporal features)

Модуль `analytics/temporal.py` агрегирует реальные транзакции по календарным датам.
Время и порядок переводов внутри дня не предполагаются. Для входящих
и исходящих переводов добавляются:

- `active_days_in`, `active_days_out`: количество различных дат с транзакциями,
  включая даты с нулевыми суммами, если такие записи есть в проверенных данных.
- `incoming_daily_max_kzt`, `outgoing_daily_max_kzt`: максимальная сумма за день.
- `incoming_daily_mean_kzt`, `outgoing_daily_mean_kzt`: средняя сумма
  **по активным дням**, а не по всем дням месяца. Если активных дней нет,
  среднее равно NaN, дневной максимум — нулю.
- `max_in_tx_per_day`, `max_out_tx_per_day`: максимальное количество транзакций
  за один день.
- `max_unique_in_senders_per_day`: максимальное количество различных отправителей
  за один день; `days_with_3plus_in_senders` — количество дат, когда их было
  не менее трёх.
- `repeated_in_counterparties`, `repeated_out_counterparties`: количество
  контрагентов с более чем одной транзакцией за переданный период наблюдения.
- `max_transactions_from_single_sender`, `max_transactions_to_single_receiver`:
  максимальное количество транзакций по одной паре. При отсутствии активности
  все количественные признаки равны нулю.

`short_window_outflow_ratio` — **эвристика**: для каждой даты поступления D
берётся минимум между входящей суммой за D и суммой исходящих переводов за
D…D+2. Полученные значения суммируются, делятся на общую наблюдаемую входящую
сумму и ограничиваются диапазоном [0,1]. Обе границы окна включены; считаются
календарные дни, даты без переводов дают ноль. `same_day_outflow_ratio`
использует только день D. Каждое окно рассматривается независимо, поэтому
при пересечении окон одна исходящая сумма может учитываться несколько раз.

Эти коэффициенты не сопоставляют конкретные транзакции и не доказывают,
что дальше были переведены те же деньги. Если положительной входящей суммы нет,
результат равен NaN. Для всех seed-клиентов оба коэффициента также равны NaN
из-за особенно неполной видимости входящих потоков. Ближе к концу периода
наблюдения отсутствие последующих дат может занижать оценку дальнейшего оттока.

## Ограничения наблюдения и диагностика

В наборе ожидаются только переводы за июль 2026 года на сумму от 5000 KZT.
Поступления из-за пределов собранного графа могут отсутствовать, особенно
у seed-клиентов. У клиентов глубины 4 могут быть невидимые исходящие переводы.
Признаки описывают только наблюдаемую активность: они не определяют остаток
на счёте, удержанные деньги, противоправность действий или полную банковскую
активность. Переводы самому себе, если они есть, учитываются по одному разу
с каждой стороны, как и в базовом графе.

Диагностика включает размер таблицы, достижимость от seed, количество узлов
с заданными порогами числа контрагентов, положительной betweenness и доступными
оконными коэффициентами, диапазон дат, изоляты, расхождения глубины, статус
анализа циклов, время отдельных расчётов и общее время расчёта и экспорта
pipeline до записи диагностики. Транзакции ниже порога или вне июля отражаются
в отчёте, а не удаляются без уведомления. Полное время процесса, включая
импорт библиотек, можно измерить через `/usr/bin/time -p`.

NaN предусмотрен только для неопределённых отношений, средних по активным дням,
расстояний от seed до недостижимых узлов и недоступных оценок HITS.
Pipeline отклоняет результаты с бесконечными значениями.
Объяснимая классификация ролей описана ниже. Кластеризация, ранжирование,
интерфейс и AI-ассистент пока не реализованы.

## Объяснимая классификация ролей — задача 4

`analytics/roles.py` назначает каждому узлу ровно одну основную роль:
`consolidator`, `transit`, `distributor`, `terminal`, `coordinator` или `peripheral`.
Размеченных правильных ответов нет: используются детерминированные правила,
без обучения с учителем. `role_score` — сила наблюдаемых признаков выбранной роли
в диапазоне [0,1], а не вероятность мошенничества, преступления или виновности.
`coordinator` означает структурную связность, а не доказанное организаторство;
`peripheral` означает отсутствие достаточно выраженного паттерна, а не безопасность.

### Нормировка и выбор порогов

Все пороги, веса и порядок выбора находятся в `ROLE_CONFIG`. Для тяжёлых хвостов
используется `positive_percentile`: средний ранг среди положительных значений,
делённый на их количество. Равные значения имеют одинаковый ранг; нули и NaN
дают 0. В столбцах `*_pct` диапазон 0…1; запись p80 в объяснении означает 0,8.
Это перцентиль **среди положительных значений**, а не среди всех клиентов.
При равных положительных значениях получается средний ранг, а не автоматически 1.
Нормировка устойчива к величине единичного экстремума, но зависит от состава
текущего набора: при изменении графа оценки могут измениться.

Перед выбором правил изучены распределения всего набора, без подбора по gid:

- `in_deg`: медиана 1, p90=2, p95=3, p99=6.
- `out_deg`: медиана 0, p90=3, p95=5, p99=23,53.
- `betweenness`: медиана 0, p90≈0,0000479, p95≈0,0001553, p99≈0,001989.
- `pagerank`: медиана ≈0,000312, p95≈0,000967, p99≈0,002212.
- `reachable_seed_count`: медиана 7, p95=10, максимум 16. Само по себе
  достижение от нескольких seed поэтому недостаточно для coordinator.
- `pass_through`: медиана 0, p75≈0,218, p90≈2,621, p95≈7,674. Большое
  отношение выход/вход не принимается за сильный транзитный сигнал.
- `short_window_outflow_ratio`: медиана 0, p90≈0,512, p95≈0,9985.

Минимум три входящих контрагента для consolidator соответствует примерно p95,
три исходящих для distributor — p90. Общий порог `min_role_score=0.65` выбран
как прозрачный рабочий порог совокупности сигналов: одного временного компонента
с весом 0,45 или признака отсутствия исходящих с весом 0,55 недостаточно.
Для transit требуются баланс ≥0,5 и оконная эвристика ≥0,5; последнее близко
к p90 её наблюдаемого распределения. Для coordinator необходим верхний квинтиль
**положительной** betweenness: `betweenness_pct>=0.8`.
Это экспертные пороги, информированные распределениями, а не статистически
подтверждённая точность или калиброванная уверенность. Размеченных данных для
оценки precision/recall нет; распределение ролей не доказывает их правильность.

### Формулы оценок (role scores)

Обозначение `P(x)` ниже — описанная выше нормировка. Все компоненты формул
также сохраняются в выходных CSV для проверки. Исходные признаки не удаляются.

- **Consolidator**: `0.40*P(in_deg) + 0.20*P(in_tx) + 0.10*P(in_kzt)
  + 0.10*seed_support + 0.10*P(max_unique_in_senders_per_day)
  + 0.10*incoming_spread`.
  `seed_support=max(P(direct_seed_in), P(reachable_seed_count))`;
  `incoming_spread=1-incoming_amount_hhi` при положительном входящем потоке.
  Допустимость: минимум 3 входящих контрагента и положительная входящая сумма.
  Один крупный перевод не удовлетворяет этому правилу.
- **Distributor**: `0.55*P(out_deg) + 0.20*P(out_tx) + 0.10*P(out_kzt)
  + 0.15*outgoing_spread`, где `outgoing_spread=1-outgoing_amount_hhi`
  при положительном исходящем потоке. Допустимость: минимум 3 исходящих
  контрагента и положительная исходящая сумма. Число получателей — главный сигнал.
- **Transit**: `0.40*transit_balance + 0.45*transit_window + 0.15*repeat_support`.
  Для положительного `r=pass_through` баланс равен `min(r,1/r)`:
  1 даёт максимум, отношения 0,5 и 2 дают 0,5; неопределённое значение даёт 0.
  `transit_window=short_window_outflow_ratio`, NaN даёт 0.
  `repeat_support` — среднее `P(repeated_in_counterparties)` и
  `P(repeated_out_counterparties)`. Допустимость: видны входящие и исходящие
  контрагенты, обе суммы положительны, баланс ≥0,5, оконная эвристика ≥0,5.
  Для **всех seed роль transit отключена**, а баланс и оконный компонент равны 0,
  даже если во входной таблице им переданы высокие коэффициенты. Достоверного
  временного сигнала при неполных входящих данных сейчас нет.
- **Terminal**: `0.55*terminal_observed_endpoint + 0.20*P(in_kzt)
  + 0.15*P(active_days_in) + 0.10*P(in_deg)`.
  Допустимость: есть входящий контрагент и положительная входящая сумма,
  `out_deg=0`, нет усечения глубиной. `terminal_observed_endpoint` равен 1
  только при выполнении этих условий. Проверяется и `truncated_by_depth`,
  и исходное условие `depth=4 && out_deg=0`, даже если флаг ошибочно снят.
  Смысл роли: «исходящих переводов не видно в наблюдаемом графе».
  Это не утверждение, что деньги остались на счёте.
- **Coordinator**: `0.60*P(betweenness) + 0.20*P(pagerank)
  + 0.20*P(reachable_seed_count)`. Допустимость: положительная betweenness,
  её нормированная оценка ≥0,8, достижимость минимум от двух seed и наличие
  входящих и исходящих связей. Объём денег не входит в формулу напрямую;
  PageRank косвенно зависит от сумм, поскольку базовый PageRank взвешенный.
  HITS не используется в оценке роли из-за возможной неединственности решения.

При отсутствии положительного потока соответствующий компонент spread равен 0.
Для недопустимых ролей оценка равна 0; рядом сохраняются флаги `*_eligible`.
Если ни одна допустимая роль не достигает 0,65, назначается `peripheral`;
её `peripheral_score` и `role_score` равны 0. Этот ноль не является оценкой риска.

### Выбор основной роли и объяснения

Функция `select_role` сначала отбирает допустимые роли с оценкой ≥0,65.
Coordinator заменяет другую подходящую роль, только если превосходит лучшую
альтернативу минимум на 0,05; если альтернатив нет, может выбираться самостоятельно.
Для остальных выбирается максимум; оценки в пределах 0,02 от максимума
считаются близкими. В таком случае порядок: transit → consolidator → distributor
→ terminal. Основание: сочетание направленного потока с временным сигналом,
затем многосторонний сбор, затем раздача и наконец отсутствие видимых исходящих.
Два процентных пункта позволяют при почти равных оценках предпочесть явный
паттерн сбора простому отсутствию оттока, например в синтетической звезде
с несколькими отправителями. Это явное экспертное правило, не порядок строк.
`role_score` всегда равен оценке выбранной роли, даже если из-за правила близости
она немного ниже максимальной оценки. Порядок строк и значения gid роли не задают.

`analytics/explanations.py` формирует русскоязычный `evidence` длиной не более
200 символов с реальными количествами, суммами или перцентилями. Суммы округляются
для компактности; полные числа остаются в исходных столбцах. Ограничения seed
и глубины 4 указываются в тексте. Оконный показатель называется эвристикой,
а не доказанным движением тех же денег. При нехватке места ограничение видимости
сохраняется, а основная часть сокращается.

### Выходные файлы и проверки

`out/node_features.csv` теперь содержит исходные признаки, нормированные
компоненты, флаги допустимости, пять оценок ролей, нулевую оценку peripheral,
`role`, `role_score` и `evidence`.

`out/nodes_roles.csv` начинается строго со столбцов:
`gid`, `role`, `role_score`, `cluster_id`, `priority_score`, `evidence`.
Остальные диагностические признаки идут далее. `cluster_id=-1` и
`priority_score=0.0` — **временные заглушки**. Кластеризация и приоритет
не рассчитываются, интерфейс и AI-ассистент не добавлены.

В `out/diagnostics.json` сохраняются применённый конфиг, количество узлов,
медианная и средняя оценка каждой роли, число peripheral, число terminal
на границе глубины 4, число seed с ролью transit и время классификации.
Для отсутствующей роли среднее и медиана равны JSON `null`.
Перед экспортом проверяются сохранность gid, уникальность, допустимые роли,
конечные оценки в [0,1], совпадение выбранной оценки и непустые объяснения
длиной до 200 символов. Для изолированных узлов предусмотрен peripheral.

  ролей, большую одиночную сумму, запоздалый отток, seed, усечённые узлы,

  присутствуют и получили peripheral. Бесконечностей, пропусков ролей или оценок нет.
- Распределение ролей; в скобках медиана / средняя оценка:
  consolidator — 112 (0,860 / 0,853), transit — 45 (0,800 / 0,789),

поведение узла, поэтому все альтернативные оценки остаются в CSV для разбора.
